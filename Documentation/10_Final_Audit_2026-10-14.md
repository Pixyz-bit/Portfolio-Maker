# Final application audit — 14 October 2026

The application builds and its normal flows mostly work, but I would not treat this version as ready for release. This audit records **23 remaining findings: 7 high priority and 16 medium priority**, plus maintenance notes. Runtime failures, source risks, and deployment observations are distinguished below. Passing compilation does not establish correctness or privacy.

The previous fixes improved password verification, transaction rollback, output encoding, permissions, session revocation, image decoding, and public-directory pagination. Further testing found a remaining data-loss case and a separate visibility interaction bug. Those gaps mean the earlier portfolio-saving and visibility fixes are not complete.

## Scope and evidence

Tests ran against a disposable IIS Express site on localhost:51904 and a unique LocalDB fixture database. Accounts, portfolios, uploads, and password changes used synthetic data. The supplied real admin credentials were not used for destructive tests or live writes. A read-only anonymous request checked the deployed login page.

The file inventory covered 126 application files, including 103 source/configuration/markup files (669,374 bytes), excluding generated bin/obj output. The review covered backend helpers, models, repositories, SQL migrations, pages and controls, JavaScript, CSS, configuration, project/publication files, and documentation. Generated designer bindings were also checked through compilation and ASP.NET precompilation. Eight font files had valid WOFF2 headers; eleven existing image assets decoded successfully.

## High priority

### 1. Malformed section JSON can still erase existing content

**Runtime and backend confirmed.** `PortfolioSaveData.ParseSection<T>` accepts `{}` as an empty `List<T>`. Posting `{}` for the skills payload returned HTTP 200 and removed existing skills. The transaction successfully commits the wrong interpretation, so rollback protection cannot prevent this loss.

Require the JSON root to be an array and validate its schema before any write. Only an explicit valid `[]` should mean “clear this section.” Add `{}`, scalar, nested-object and missing-property regression cases.

Location: [241611JalopPersonalWebsite/Backend/Model/PortfolioSaveData.cs](<C:/Martin Archive/Programming/ASP NET/241611JalopPersonalWebsite/241611JalopPersonalWebsite/Backend/Model/PortfolioSaveData.cs:17>), especially deserialization at line 22; [Backend/Repository/PortfolioSaveRepository.cs](<C:/Martin Archive/Programming/ASP NET/241611JalopPersonalWebsite/241611JalopPersonalWebsite/Backend/Repository/PortfolioSaveRepository.cs>) replaces section rows.

### 2. Clicking the visibility card can falsely say a public portfolio is private

**Browser and anonymous HTTP confirmed.** Clicking the card's text changed “Public Portfolio” to “Private Portfolio” without saving. An anonymous request still read the sample biography with HTTP 200, and reload restored “Public Portfolio.” The switch itself successfully saved when directly activated.

`triggerToggle` sets `isSubmitting=true`, then the card path calls `toggleBtn.click()`. The button's handler re-enters `triggerToggle`, sees that flag and prevents the postback. This produces an optimistic status that can be dangerously misleading.

Use one submission path, set the guard only for the actual submission, and reconcile displayed state with the confirmed server result. Test clicks on the text, card background, switch, Enter and Space in both directions.

Location: [Frontend/Assets/js/user-menu.js](<C:/Martin Archive/Programming/ASP NET/241611JalopPersonalWebsite/241611JalopPersonalWebsite/Frontend/Assets/js/user-menu.js:66>), lines 99–116. Evidence: `final-audit-visibility-card.json` and `visibility-card-false-private.jpg`.

### 3. Account Settings bypasses the admin self-deactivation safeguard

**HTTP and database confirmed.** Admin dashboard actions reject deactivation of the current admin, but the same admin can uncheck Active in their own Account Settings. The database changed to inactive and subsequent access lost authentication. The test restored the disposable account. There is also no central last-active-admin guard; self-demotion/other-admin changes can leave no usable admin account (source risk).

Enforce self-deactivation and last-admin invariants centrally in the repository/transaction, not separately in individual click handlers. Include concurrent administrator changes in that invariant.

Location: [Frontend/User/Controls/UserMenu.ascx.cs](<C:/Martin Archive/Programming/ASP NET/241611JalopPersonalWebsite/241611JalopPersonalWebsite/Frontend/User/Controls/UserMenu.ascx.cs:90>), lines 150–179; dashboard safeguard at [Frontend/Admin/Dashboard.aspx.cs](<C:/Martin Archive/Programming/ASP NET/241611JalopPersonalWebsite/241611JalopPersonalWebsite/Frontend/Admin/Dashboard.aspx.cs:395>); [Backend/Repository/UserRepository.cs](<C:/Martin Archive/Programming/ASP NET/241611JalopPersonalWebsite/241611JalopPersonalWebsite/Backend/Repository/UserRepository.cs:629>).

### 5. The migration described as a “safe re-run” drops user data

**Source confirmed; deliberately not executed against an existing real database.** `01_Schema.sql` drops Skills, Hobbies, Educations, UserProfiles and Users. Re-running it can erase accounts and portfolio data. Later foreign-key tables are absent from its drop order, so on an evolved schema it can also stop after only part of the destructive sequence.

Separate a clearly labeled fresh-database bootstrap from versioned, nondestructive migrations. Add a refusal guard for nonempty databases and transactional migration/version tracking. Do not run this script as an ordinary update.

### 7. The deployed login route still accepts plain HTTP

**Live anonymous GET confirmed.** The deployed login URL returned HTTP 200 with final scheme `http`, rather than redirecting to HTTPS. No credentials were submitted during this check. Configure valid HTTPS at the host, redirect HTTP, and apply appropriate Secure/HttpOnly/SameSite cookie settings. Verify this on the actual host; local HTTP fixture behavior is not evidence of production TLS settings.

## Medium priority

### 8. One admin form save can partially commit despite password validation failure

**HTTP and database confirmed.** Editing a synthetic account's name and entering a short new password changed the name before reporting the password error. The code explicitly tells the user about that partial result, but a single Save action is not atomic. Account Settings likewise writes account details, visibility and password separately; a later operation can fail after earlier changes commit (source risk).

Validate every submitted field first and commit the intended operation in one transaction, or separate independent actions clearly in the UI.

### 9. Login has no application-level retry throttling

**Source finding; hosting controls and load behavior unverified.** There is no failed-attempt limit, backoff or rate-limiter in the application login path. Password verification also runs while the database reader/connection remains open. Repeated login attempts can consume both hashing CPU and connection capacity.

Apply bounded per-account/per-client rate controls with appropriate recovery behavior, and release the database reader before expensive verification where practical. Do not interpret this audit as a load-test result.

**HTTP and backend confirmed.** Signup accepted a 51-character first name but stored 50. Admin creation accepted 70 characters and stored 50. SQL parameters impose the size, while those repository paths do not reject overlong values. Some admin fields also lack matching client limits.

Validate maximum lengths consistently on the server and in the UI. Reject values with a clear field error instead of silently changing them.

## Maintenance and deployment notes

- URL obfuscation uses a fixed key/IV embedded in source and no integrity tag ([Backend/Common/UrlObfuscator.cs](<C:/Martin Archive/Programming/ASP NET/241611JalopPersonalWebsite/241611JalopPersonalWebsite/Backend/Common/UrlObfuscator.cs:12>)). It should not be described as tamper-proof or as an authorization boundary. Actual server authorization is what protects private content; no authorization bypass through token forgery was demonstrated. Use an opaque identifier or authenticated token if token integrity is needed, and correct [Documentation/02_Url_Obfuscation_Security_Guide.md](<C:/Martin Archive/Programming/ASP NET/241611JalopPersonalWebsite/Documentation/02_Url_Obfuscation_Security_Guide.md>).
- Old profile Create/Update helpers still perform visibility work separately and ignore its failure. The current editor uses the newer save repository, so this is a future-call-site risk rather than a reproduced current editor failure. Remove obsolete paths or bring their guarantees into line.
- Logout is performed through a GET link. A cross-site navigation can therefore trigger logout. Prefer a protected POST for this state change.
- Some documentation overstates completed cleanup: the assets-separation guide claims all inline CSS/JavaScript was removed, while inline styling remains. Keep migration instructions, security claims and deployment notes aligned with executable behavior.
- WebP decoding relies on Windows WIC codec availability. It worked here, but the target server still needs verification. No unsupported-codec production failure was observed.
- The incumbent visual style was preserved. Automated design-detector warnings about fonts, borders or easing were not treated as functional defects without relevant evidence.
- The deployed site appears older than the local audited source. Passing local tests does not establish that a live deployment contains the fixes. Deployment was not performed during this audit.

## Limits and next steps

Finite tests cannot cover every possible input, concurrency schedule, browser or hosting configuration. This audit exercised control/input families and meaningful boundary cases, rather than claiming every repeated row action or arbitrary payload combination is proven correct. Native PDF export was invoked, but a completed PDF artifact and its page layout were not verified. Real devices, multiple browser engines, screen-reader operation, high-concurrency load, SQL outage fault injection and host-level rate limiting/TLS/cookie configuration need separate checks.

Fix findings 1–7 first, then add regression cases for the exact reproduced failures before release. Follow with atomic account saves, validation consistency, image lifecycle/size, installation/publication reliability, feedback, pagination and responsive/accessibility details. This turn added audit/reproduction files and evidence; it did not change production application code or deploy the site.

Cleanup completed: the disposable IIS Express instance and fixture database were removed, temporary browser tabs were closed, and the verified workspace `Tests/Temp` directory was removed after preserving nonsecret evidence. The final whitespace check passed.
